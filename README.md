# ФСП Карьера

Платформа подбора ИТ-специалистов **с обратной механикой**: кандидаты распределяются по категориям
(специализация × грейд) по результатам адаптивного тестирования и подтверждённых достижений Федерации спортивного
программирования, а работодатель сам находит нужную категорию и выходит на конкретного человека — с предложением и
обязательной вилкой зарплаты. Контакты кандидата раскрываются только после его согласия.

Решение для специального трека ФСП хакатона «Лидеры цифровой трансформации — 2026».

## Быстрый старт (Docker)

Нужен Docker Desktop (или Docker Engine + Compose v2). Свободные порты: 8080, 8000, 8090, 8025.

```bash
docker compose up --build
```

Первый старт: сборка образов ~5–8 минут, затем бэкенд создаёт схему БД и наполняет демо-данными: 700 кандидатов, компании, вакансии (~20–30 секунд).
Стенд готов, когда http://localhost:8080 открывает главную страницу. Остановка — `docker compose down`
(данные сохраняются в томе `pgdata`; полный сброс — `docker compose down -v`).

Суммарный лимит памяти контейнеров ≈ 2,5 ГБ (PostgreSQL 512 МБ, бэкенд 1 ГБ, песочница 512 МБ, остальные — по 128–192 МБ). Песочница для кода кандидатов работает без сети и не публикует портов.

### Сценарий демонстрации (≈ 8 минут)

1. **Регистрация соискателя** — `/register`: e-mail, пароль, согласие 152-ФЗ → код подтверждения (в демо-режиме
   показывается на экране и приходит в Mailpit). Или войдите как `newbie@demo.ru`.
2. **Профиль** — «Загрузить PDF»: резюме с hh.ru (двухколоночная вёрстка) или любое другое — ФИО, контакты и GitHub,
   желаемая должность и зарплата, формат, места работы с датами, стаж, образование, языки, стек, роли и софт-скиллы.
3. **Опрос и тест** — специализация, язык, опыт, предполагаемый грейд → адаптивный тест (12–24 задания, у каждого
   кандидата уникальные варианты, время зависит от формата и трудности задания). Прокторинг: нажмите PrintScreen —
   появится предупреждение; повторно — тест завершится досрочно с пониженной оценкой. Результат: решение по грейду,
   процентиль, профиль по доменам.
4. **Вторая специализация** — «Опрос и тест» → «Новая специализация» (или «Профиль» → «Добавить резюме»): опрос и
   отдельный тест дают вторую категорию; у `candidate@demo.ru` уже есть Backend · Middle и DevOps · Junior.
5. **ФСП ID** — «Настройки» → «Привязать ФСП ID» → вход `alice / fsp12345` → достижения подтянулись из реестра.
6. **Работодатель** (`employer@demo.ru`) → «Подборки» → опишите потребность текстом (есть готовые примеры)
   → рекомендованные категории с медианой ожиданий и долей «в вашей вилке» → ранжированные кандидаты
   с объяснением «почему в подборке» → фильтры поверх сохранённой подборки.
7. **Выход на контакт** — «Пригласить»: вилка обязательна, видна оценка вероятности отклика; приглашение уходит
   по конкретному резюме (категории) → кандидат видит предложение с условиями → принимает → контакты открываются
   обеим сторонам (или отклоняет с причиной). Просмотр профиля работодателем контакты не раскрывает.
8. **Классический отклик** — кандидат: «Вакансии» → отклик выбранным резюме; работодатель видит отклики с оценкой совпадения.
9. **Тест по вакансии** — работодатель: потребность → вкладка «Тест по вакансии»: блюпринт, примеры заданий и три
   варианта одного семейства для разных кандидатов.
10. **Задача с кодом** — кандидат: «Задания» → задача «Нормализация телефонных номеров» → редактор → «Запустить примеры» (код исполняется в песочнице) → «Отправить решение» (открытые и скрытые тесты). Работодатель: «Задания» → решения на проверке с результатами всех тестов, отметкой антиплагиата и сигналами редактора; «Новое задание» → тип «Задача с кодом»: функция, тесты, эталон, который проверяет сами тесты.
11. **Методика** — `/methodology`: результаты валидации тестирования, устойчивости к утечкам и подбора.

## Что внутри

### Ключевые механики

**Тестирование, устойчивое к распространению заданий**
- Банк из **359 семейств заданий** по 27 доменам (125 параметрических). Семейство — шаблон с откалиброванной
  трудностью; для каждого кандидата генерируется свой вариант: свои данные, массивы, таблицы (SQL-запросы реально
  выполняются в SQLite), код на основном языке кандидата (Python / JavaScript / Java / Go). Ответ вычисляется.
- **Адаптивный тест (CAT) на модели IRT 3PL**: выбор задания по максимуму информации Фишера с балансировкой
  доменов по блюпринту специализации и контролем экспозиции; оценка уровня θ — EAP с общим prior, поэтому
  результаты кандидатов с разными наборами заданий сопоставимы.
- Решение по грейду: подтверждён, если P(θ ≥ нижней границы грейда) ≥ 0.6; «уверенно» — если с вероятностью
  ≥ 0.8 выше верхней границы: тогда тест уровнем выше доступен без ожидания, но запускает его сам кандидат, когда
  готов. Не подтвердил — грейд ниже можно принять по тому же тесту, если тест уверенно (P ≥ 0.8) его показал (верно
  в 99.8% случаев), или пройти тест уровнем ниже; повышение — только отдельным тестом (по тому же тесту было бы верно
  лишь в 73%). Любой тест начинается после подтверждения готовности. Грейд не понижается принудительно; смена
  грейда и повтор уровня — не чаще раза в месяц.
- **Три детектора нечестности**: ответ «чужого варианта» (списанный ответ не подходит к своему варианту),
  дрейф решаемости задания относительно модели (утечка статичных заданий → автоматический вывод из ротации),
  person-fit lz и слишком быстрые верные ответы на трудные задания.
- **Прокторинг**: снимок экрана (PrintScreen, Win+Shift+S, ⌘⇧3/4/5), печать и копирование задания — первое
  нарушение даёт предупреждение, второе завершает тест досрочно со штрафом −0.5 к оценке уровня θ; правило
  применяет сервер, содержимое экрана не записывается. Время на ответ — базовое по формату с поправкой на
  трудность задания (−20%…+35%).
- Пилотные задания (в том числе черновики, сгенерированные LLM) встраиваются без влияния на оценку и
  калибруются онлайн по реальным ответам — так генеративные задания получают сопоставимую трудность.

**Задачи с кодом в песочнице**
- Работодатель задаёт функцию (Python или JavaScript), шаблон, открытые тесты-примеры, скрытые тесты и эталон;
  эталон при сохранении прогоняется на всех тестах — ошибка в ожидаемых ответах не пройдёт.
- Кандидат решает в редакторе, запускает код на примерах и отправляет; по скрытым тестам видит только «пройден / нет».
  Автооценка — доля пройденных тестов; ответы скрытых тестов в песочницу не передаются.
- Песочница — отдельный контейнер **без сети** (`network_mode: none`, бэкенд стучится через Unix-сокет), файловая
  система только для чтения, отдельный пользователь, лимиты CPU, памяти, файлов и процессов; проверена враждебным
  кодом: сеть, запись, fork-бомба, «сбежавшие» процессы.
- **Антиплагиат** по структуре кода (токены + winnowing, как MOSS): переименование и форматирование не скрывают
  копию. **Защита от подсказок LLM**: работодатель видит вставки из буфера, уходы со вкладки, время и число запусков.

**Подбор с обратной механикой**
- Потребность работодателя (текст вакансии) разбирается NLP: специализация (TF-IDF + логистическая регрессия
  в гибриде с правилами по онтологии из 105 навыков), грейды, обязательные и желательные навыки, вилка, формат, город.
  Все суммы на платформе — до вычета НДФЛ и так подписаны; «на руки» в текстах пересчитывается.
- Пул кандидатов — только из **категорий, присвоенных тестом**; рекомендуются основная категория, соседние грейды
  и смежные специализации — с аналитикой рынка (медиана ожиданий, доля в вилке, число с достижениями ФСП).
- Ранжирование: `(0.30·навыки + 0.25·сила профиля + 0.20·категория + 0.15·условия + 0.10·текст) · доступность`,
  где сила профиля = 0.6·тест + 0.25·ФСП + 0.15·регулярные задания (тестовая часть — относительно запрошенного
  грейда). Навыки получают статус по свидетельствам теста на уровне требований вакансии: «подтверждён»,
  «заявлен», «не подтвердился». Каждая карточка объясняет, почему кандидат в подборке.
- Приглашение: вилка «от–до» обязательна, привязка к вакансии необязательна, оценка вероятности отклика,
  статусы «отправлено → просмотрено → принято / отклонено (с причиной) / истекло / отозвано».
- **Несколько резюме — несколько категорий**: до трёх специализаций на кандидата, у каждой свой опрос, тест и
  категория. Единица пула подбора — резюме; кандидат показывается один раз — с лучшим под потребность резюме,
  приглашения и отклики привязаны к конкретному резюме.

**Интеграция с ФСП**
- Привязка и вход через **ФСП ID** по OpenID Connect (authorization code + PKCE, проверка id_token по JWKS).
  Пути эндпоинтов совпадают с Keycloak (`/realms/<realm>/protocol/openid-connect/...`) — для подключения к реальному
  ФСП ID достаточно сменить `FSP_PUBLIC_ISSUER` и учётные данные клиента.
- Реестр достижений: соревнования, уровень, дисциплина, место, команда, разряд, рейтинг. Как рекомендовали
  постановщики, учитываются результативность и число соревнований (дисциплины равнозначны, участия без результата —
  с потолком), и достижения двигают кандидата внутри категории, но не меняют грейд. Кандидат без истории ФСП
  участвует в подборе наравне — достижения дают только бонус к силе профиля.

### Результаты валидации

Эталонной разметки нет, поэтому построена собственная процедура на синтетической популяции с известной «истиной»

воспроизведение — `python -m validation.run_all` (≈2,5 минуты).

| Метрика | Значение |

| Завышение грейда | 3.1% (в резюме — 36%) |
| Повторный тест: взвешенная κ / r(θ̂₁, θ̂₂) | 0.80 / 0.82 |

| Подбор: P@10 / nDCG@10 / MRR | 0.84 / 0.82 / 0.96 (фильтры по резюме — 0.75 / 0.80 / 0.90; поиск по ключевым словам — 0.27) |

### Архитектура

```mermaid
flowchart LR
  U[Браузер] -->|HTTPS| N[nginx: SPA + обратный прокси]
  N -->|/api| B[Backend FastAPI]
  B --> P[(PostgreSQL)]
  B -->|SMTP| M[Mailpit]
  B -->|OIDC: token, JWKS| F[ФСП ID mock / Keycloak]
  B -->|REST + API key| R[Реестр достижений ФСП]
  B -->|Unix-сокет| S[Песочница: Python, Node.js, без сети]
  U -->|OIDC: страница входа| F
  subgraph Backend
    B1[api: auth, candidate, testing, employer, fsp, public]
    B2[services: testing CAT/IRT + банк, matching, nlp, fsp, pdf, sandbox]
  end
```

Модульный монолит с явным разделением слоёв: `api` (роутеры, валидация, права) → `services` (бизнес-логика без
HTTP) → `models` (SQLAlchemy). Ядро тестирования (`services/testing/cat.py`, `irt.py`) не зависит от БД и
переиспользуется в симуляциях валидации. Бэкенд stateless — масштабируется репликами.

## Локальный запуск без Docker

Требования: Python 3.11, Node.js 20+.

```bash
# 1. Бэкенд (по умолчанию SQLite в backend/data, демо-данные создаются при первом старте)
python -m venv .venv
.venv/Scripts/activate            # Linux/macOS: source .venv/bin/activate
pip install -r backend/requirements.txt
cd backend && uvicorn app.main:app --port 8000

# 2. Mock ФСП ID и реестра (в отдельном терминале)
pip install -r fsp-mock/requirements.txt
cd fsp-mock && uvicorn app.main:app --port 8090

# 3. Фронтенд (в отдельном терминале) — http://localhost:5173, запросы /api проксируются на :8000
cd frontend && npm ci && npm run dev
```

Тесты и валидация:

```bash
cd backend
python -m pytest -q                 # 508 тестов: банк заданий, сквозной сценарий, видимость, резюме и категории, прокторинг, задачи с кодом и песочница, антиплагиат, PDF, NLP
python -m validation.run_all        # полный прогон валидации → validation/reports/*.json, SUMMARY.md
```

## Безопасность и 152-ФЗ

- Согласие на обработку ПДн — обязательно при регистрации; согласие на публикацию профиля — отдельно; журнал
  согласий с датой и устройством; отзыв согласия скрывает профиль. Выгрузка всех своих данных и удаление аккаунта.
- Контакты кандидата скрыты до принятия приглашения или собственного отклика; доступ к контактам журналируется.
  По умолчанию работодатель видит анонимный код вместо имени (снижает предвзятость).
- Пароли — Argon2id; коды подтверждения хранятся как HMAC; JWT с ограниченным сроком; ограничение частоты попыток
  входа; разграничение прав по ролям на каждом эндпоинте; кандидат видит только свои приглашения и отклики.
- Защита от недобросовестных работодателей: суточный лимит приглашений, индекс доверия компании (домен e-mail ↔ сайт,
  жалобы кандидатов), жалоба на приглашение, кандидат может скрыть предложения ниже своих ожиданий.
- Код кандидатов исполняется только в контейнере песочницы без сети; ответы скрытых тестов в неё не передаются.
